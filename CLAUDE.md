# Портфолио — Анастасия Плетнер (Pletner Design)

Личный дизайн-портфолио на React 19 + TypeScript + Vite. Витрина концептов
UI/UX-проектов ("Аптеки рядом", "Movie Mate", "CampaignCore",
"Coffee Break Languages").
Визуальный стиль — коллаж/скрапбукинг (вырезки из бумаги, нитки, звёзды).

## Структура

- `src/components/Header`, `src/components/Footer` — общий каркас (шапка с лого, футер со ссылками)
- `src/pages/Main` — главная: `Hero` (о себе) + `MainContent` (грид проектов)
- `src/pages/ProjectPage` — страницы отдельных кейсов (Apteki, Dashboard и т.д.)
- `src/data.ts` — список проектов для карточек на главной
- `src/UI` — общие компоненты (`Button`) и `sharedStyles.module.css` (обёртки, отступы, акцентный цвет)
- CSS Modules везде, без глобального стейт-менеджмента

32. **Побочный эффект п.31**: правило на `html` из предыдущего пункта
    случайно погасило текстуру фона (`body::before`) — стала не видна
    совсем. Причина — CSS root-canvas propagation: пока `html` был без
    фона, фон `body` "пробрасывался" на canvas и сама коробка `body` не
    красилась (спека HTML/BODY background propagation), поэтому
    `body::before` с `z-index:-1` был самым нижним слоем и текстура была
    видна. Как только у `html` появился явный `background-color`,
    пробрасывание отключилось, `body` стал красить свой непрозрачный фон
    как обычный элемент (он ведь `position:relative` без своего
    stacking context) — и это закрасило текстуру, которая в отсутствие
    у `body` собственного stacking context всплывала в корневой контекст
    и красилась ДО фона body, а не после. Починила добавлением
    `isolation: isolate;` на `body` — создаёт body свой стекинг-контекст,
    внутри которого порядок отрисовки: сначала фон body, потом
    `::before` (z-index:-1) поверх него, потом обычный контент. Если
    в будущем текстура снова "пропадёт" после правок в `index.css` —
    проверить в первую очередь именно это: `html`/`body` background
    propagation + отсутствие stacking context на `body`.

    особенностях" визуально не совпадали с `.versionLabel`** ("Первая
    версия"/"Финальная версия"/"Почему поменяли") — не в `font-weight`

    глобального `.projectPage h2, h4, h5 { font-family: Gilroy-600;
    ... }` в `page.css` (по specificity `:global(.projectPage)
    h4.featureHeading` = 0,2,1 перебивает font-size/margin-bottom из
    той же строки, но НЕ font-family — та осталась не переопределена,
    т.к. я её не объявляла). Т.к. Gilroy в проекте — набор отдельных
    файлов, а не variable font (см. п.45/48), "Gilroy-600" в имени
    файла — это буквально файл Gilroy-Medium, визуально более жирный,
    чем "Gilroy-400" (Gilroy-Regular), которым рендерится
    `.versionLabel`. Нашла через `getComputedStyle` (сравнила
    `fontFamily` двух элементов бок о бок), не на глаз. **Фикс**:
    добавила явный `font-family: Gilroy-400;` в `.featureHeading`.
    Проверила заново через `getComputedStyle` — теперь `fontSize`/
    `fontStyle`/`fontFamily`/`color` у `.versionLabel` и
    `.featureHeading` совпадают идентично (кроме `margin-bottom`,
    который не про текст, а про интервал, и разный у них осознанно из
    п.47). **Урок**: когда объявляешь CSS-класс с `:global(.projectPage)
    <тег>.<класс>` паттерном (обход specificity-гочā из п.27), высокая
    specificity действует только на свойства, которые класс реально
    объявляет — если у глобального конкурирующего правила есть ещё
    какое-то свойство (тут `font-family`), которое твой класс не
    перечислил, оно всё равно просочится и переопределит унаследованное
    только частично. Нужно либо объявлять все конфликтующие свойства
    явно, либо сверять `getComputedStyle` по каждому свойству, а не
    только по тому, которое чинил в моменте.

      collapse вообще, сразу считать сумму margin-bottom+margin-top и
      проверять `getBoundingClientRect()`, а не только на глаз.
